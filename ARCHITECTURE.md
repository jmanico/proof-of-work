# ARCHITECTURE.md

### Required Architecture Inputs

- **Requirements source:** REQUIREMENTS.md
- **Design source:** DESIGN.md
- **System purpose:** A fitness web application delivering science-based, admin-curated exercise and diet plans, allowing subscribers to customize those plans into private copies, and tracking their progress over time. Access requires a paid subscription. (REQUIREMENTS.md, Project purpose)
- **Primary use cases:** Register and authenticate; subscribe; browse and select an exercise or diet plan; customize a plan into a personal copy; log workouts, food intake, weight, and measurements; view progress over time; admin authors, cites, verifies, and publishes plans; consultant accesses an engaged subscriber's data. (REQUIREMENTS.md, Core workflows; FR-11.x)
- **Target users / actors:** Subscriber; Fitness consultant / helper (paid option); Admin. (REQUIREMENTS.md, Primary users / actors)
- **Runtime environment:** Web application, responsive across current desktop and mobile browsers (FR-1.1, FR-1.2). No native client.
- **Server framework:** Node.js (architecture notes), with Fastify as the framework within it and TypeScript as the language (CLAUDE.md, Repository state).
- **Client framework:** Vue.js (architecture notes), built by Vite as a single-page application with `vue-router`, written in TypeScript (CLAUDE.md, Repository state). No server-rendering tier exists; the five components below remain the whole system.
- **API style and integration model:** REST over HTTPS between browser client and server (architecture notes). No external integrations — the system is self-contained (REQUIREMENTS.md, External integrations; FR-9.8).
- **Authentication and session model:** Email + password with optional user-enabled MFA for subscribers; passkey required for admin and consultant accounts (architecture notes; FR-2.2, FR-2.3, FR-2.5, FR-2.6, FR-2.8, FR-2.9). Session transport and revocation: a signed token carrying a session identifier and no authorization state, in an `HttpOnly`, `Secure`, `SameSite` cookie, resolved against a server-side session record on every request and revoked by invalidating that record (SECURITY.md SEC-SESSION-3, SEC-SESSION-5; SQ-2 RESOLVED). Session lifetimes are fixed (SQ-3 RESOLVED): subscriber 24 h absolute / 2 h idle, privileged 12 h / 30 min.
- **Data model expectations:** Relational (RDBMS) (architecture notes). Entities from REQUIREMENTS.md: user account; subscription; consultant engagement; exercise catalog entry (FR-5.4); exercise plan and diet plan (each with cited sources and verification record); user plan copy; workout log entry; food log entry; nutrition dataset item (imported at build or deploy time, FR-8.11); body weight entry; body measurement entry; consent record; medical-disclaimer acknowledgement (FR-9.6, versioned); pending deletion request (FR-9.11); audit entry; session record, email-verification token, MFA enrolment, MFA recovery code, password-reset token, and privileged enrolment invitation; throttle and quota counters (SECURITY.md SEC-AUTHN-6, SEC-HTTP-5); the versioned breached-password list artifact (SEC-AUTHN-6). The deletion ledger lives in the log-archive account, outside the restored dataset (SEC-DATA-4). Engine is PostgreSQL and migrations are managed by Drizzle ORM with drizzle-kit (CLAUDE.md, Repository state). Schema design and indexing: decided with the code. Retention behavior is resolved (SECURITY.md SQ-5, SQ-8; FR-8.14 lifetime history).
- **Deployment model:** Terraform-managed infrastructure on AWS (architecture notes). Services and topology are fixed (SECURITY.md SQ-7 RESOLVED): three environments in separate AWS accounts (dev/staging/production); ECS Fargate for the API, S3 + CloudFront for the client, RDS PostgreSQL Multi-AZ in isolated subnets, Amazon Bedrock in-account for AI inference, Amazon SES in-account for transactional email (SEC-EXT-3, 2026-08-03), AWS Secrets Manager for secrets and signing keys; GitHub Actions deploys via per-environment OIDC roles. CloudFront is the single public origin: it serves the static client from S3 and forwards the API path prefix to the ALB, realizing the SQ-6 same-origin surface (2026-08-03).
- **Scale expectations:** Global (architecture notes). Concrete load, latency, and availability targets: UNKNOWN. Data residency is resolved (SECURITY.md SQ-1): single US primary region with standard lawful cross-border transfer mechanisms; GDPR is the design ceiling and imposes no EU-residency requirement.
- **Security expectations:** Defined in SECURITY.md, including the initial document-based threat model (2026-07-31), which added trust boundaries 4 and 5 below.

### Initial Architecture (Provisional)

Five components: the browser client, the server-side REST application, relational persistence, identity/session handling within the server, and AI inference within the system's cloud boundary (added 2026-08-01 by the OQ-5 resolution). There is no external-integration boundary and no message broker, because the system is specified as self-contained and must not transmit health data externally (FR-9.8). Outbound transactional email — address verification, password reset, privileged invitations, pending-deletion notices — leaves the system through an in-account managed email service behind an internally defined mail interface (SECURITY.md SEC-EXT-3, 2026-08-03); it carries no health data and is a channel, not a component. No background-processing boundary exists for user-facing operations: data export and account deletion run synchronously (SECURITY.md SQ-5 RESOLVED). The REST API Application additionally runs scheduled executions — same codebase, image, and database identity — for the nightly audit archival (SEC-LOG-7), deletion-ledger maintenance (SEC-DATA-4), and FR-9.11 window expiry (2026-08-03); these are executions of an existing component, not a new one.

All business rules are enforced server-side. The client renders and validates for usability only; it is never the authority for authorization, entitlement, or data validity.

- **Browser Client (Vue.js)**
  - **Responsibility:** Render all user-facing views and forms; issue REST calls; present plan content and citations; present progress history; enforce the interaction and accessibility conventions in DESIGN.md — visible focus indicators, keyboard operability, inline field-level error presentation with focus moved to the first invalid field, color-independent status signalling, responsive reflow with no loss of function on mobile (FR-1.2), reduced-motion handling, and 200%-zoom/320px reflow. Performs client-side input validation for immediate feedback only.
  - **Inputs:** User interaction; REST responses including validation errors, authorization failures, and entitlement failures.
  - **Outputs:** REST requests; rendered UI; accessible status and error announcements.
  - **Data owned or accessed:** Owns no durable data. Holds transient view state and session credentials as issued by Identity and Session Handling.
  - **Open decisions:** None at the presentation-system level. Progress history uses trend charts paired with accessible tables at entry granularity (REQUIREMENTS.md OQ-7 RESOLVED; FR-8.14; DESIGN.md OQ-4). Plan statements use inline numbered references connected to an Evidence section, with a dated subscriber-facing review line and admin-only verifier detail (DESIGN.md OQ-5). The medical disclaimer uses a first-plan acknowledgement interstitial plus a persistent safety link; health-data consent remains a separate explicit flow before the first health-data write (FR-9.2, FR-9.6; DESIGN.md OQ-6). Subscriber, consultant, and admin workspaces and their responsive navigation are defined by DESIGN.md OQ-7. Client-side rendering and routing are resolved: a Vite-built single-page application with `vue-router`, styled with plain CSS custom properties and scoped single-file-component styles (CLAUDE.md, Repository state). Offline capability is confirmed out of scope (REQUIREMENTS.md OQ-14 RESOLVED).

- **REST API Application (Node.js)**
  - **Responsibility:** Single server-side entry point and the sole authority for business rules. Authenticates every request via Identity and Session Handling; enforces role rules (FR-2.7, FR-10.1), subscription entitlement (FR-3.1, FR-3.2), owner scoping (FR-7.4, FR-9.1), and consultant engagement scoping (FR-11.2, FR-11.3) before any data access. Enforces publication gates (FR-4.4, FR-4.5, FR-4.7), unpublication's selection-ending effect (FR-4.9), copy-on-customize semantics (FR-7.2, FR-7.5), log-entry validation (FR-8.9), consent capture (FR-9.2), the admin health-data prohibition (FR-10.3, SECURITY.md SEC-AUTHZ-9), and audit writes on health-data access (FR-9.7, FR-11.4). Owns the admin-curated exercise catalog (FR-5.4) and the FR-9.11 pending-deletion lifecycle, and sends pending-deletion notices through the mail interface (SEC-EXT-3). Owns every business object described below.
  - **Inputs:** Authenticated REST requests from the Browser Client; persisted state.
  - **Outputs:** REST responses; validation and authorization errors carrying the specific failing field or reason so the client can present them per DESIGN.md; persistence reads and writes; audit entries.
  - **Data owned or accessed:** Owns user account, subscription, consultant engagement, exercise catalog entry, exercise plan, diet plan, plan citations and verification records, user plan copy, workout log entry, food log entry, body weight entry, body measurement entry, consent record, disclaimer acknowledgement, pending deletion request, and audit entry. Accesses all of them through Relational Persistence.
  - **Open decisions:** Internal module decomposition is RESOLVED (2026-08-03): the application is a modular monolith of domain modules — identity (the Identity and Session Handling component, kept behind its interface per DR-8), plans, catalog, customization, progress, entitlement, consultant, privacy/data-rights, and audit — each owning its own routes, service logic, and data access, over a shared kernel holding the SEC-AUTHZ-5 policy module, the DR-9 audit writer, the SEC-EXT-3 mail interface, and shared validation. Modules depend on the kernel and on one another only across documented interfaces, without cycles (DR-6); none is a separate deployable. Export and deletion execute synchronously (SECURITY.md SQ-5 RESOLVED): no background-processing boundary exists and no export artifact is stored. Subscription activation is resolved: admin-granted periods, audited (REQUIREMENTS.md OQ-1 RESOLVED; FR-3.5, FR-3.6), with the paid consultant option recorded the same way (FR-11.5) and self-serve payments deferred (OQ-18). Nutrition data is resolved: a bundled dataset imported at build or deploy time plus in-boundary AI estimation (REQUIREMENTS.md OQ-5 RESOLVED; FR-8.11–FR-8.13). Consultant capabilities are resolved: views plus edits of the engaged subscriber's plan copies, audited (REQUIREMENTS.md OQ-12 RESOLVED; FR-11.6). Verification is resolved as a one-time gate that never re-triggers on edit, with the citation invariant enforced at edit time (REQUIREMENTS.md OQ-10, OQ-16 RESOLVED; FR-4.8).

- **Identity and Session Handling**
  - **Responsibility:** Server-side registration, credential verification, MFA challenge for subscribers who enable it, passkey registration and verification for admin and consultant accounts, session establishment and termination, and role resolution supplied to the REST API Application for every request. Rejects invalid credentials without revealing which factor failed (FR-2.3).
  - **Inputs:** Registration, authentication, MFA, passkey, and logout requests; stored credential and passkey material.
  - **Outputs:** Authenticated session context including account identity and role; authentication failures; session termination; verification, password-reset, and invitation email sent through the mail interface (SECURITY.md SEC-EXT-3).
  - **Data owned or accessed:** Owns credential material, MFA enrolment state, passkey registrations, and session state. Reads user account identity and role.
  - **Open decisions:** Whether this is a module of the Node.js application or a separately deployed service — TO BE DECIDED; either way it is a distinct trust boundary. Session transport, revocation, MFA factors, password policy, and privileged provisioning are specified in SECURITY.md (SEC-SESSION-3, SEC-SESSION-5, SEC-AUTHN-5, SEC-AUTHN-6, SEC-AUTHN-8, SEC-AUTHN-9). Session lifetimes are fixed (SECURITY.md SQ-3 RESOLVED). Account-recovery and MFA-recovery flows are governed by SECURITY.md SEC-AUTHN-10, SEC-AUTHN-11, and SEC-AUTHN-12; REQUIREMENTS.md OQ-8 is fully RESOLVED. This component's authentication surface now has no undecided behavior or parameters; key storage is resolved (SQ-7: AWS Secrets Manager with `kid`-based 90-day rotation, SEC-SESSION-7). Credential storage and cryptographic controls are deferred to SECURITY.md.

- **Relational Persistence (RDBMS)**
  - **Responsibility:** Durable, transactionally consistent storage for all business objects. Enforces referential integrity and ownership relationships in schema. Must retain progress records and plan customizations across subscription lapse (FR-3.4) and preserve customized copies when their source plan changes (FR-7.5).
  - **Inputs:** Reads and writes issued exclusively by the REST API Application and Identity and Session Handling.
  - **Outputs:** Persisted state; integrity constraint violations.
  - **Data owned or accessed:** Stores all entities listed under Data model expectations. Stores no user data that originates outside the system; the bundled nutrition dataset (FR-8.11) is the sole imported external content stored here, ingested at build or deploy time as a versioned, integrity-verified artifact — the breached-password list (SECURITY.md SEC-AUTHN-6) follows the same versioned-artifact discipline wherever it is held.
  - **Open decisions:** Schema design and indexing — implementation-level, decided with the code. Audit retention is resolved (SECURITY.md SQ-8: 12-month logs, 3-year audit entries, hash-chained archive). Deletion mechanics are resolved (SECURITY.md SQ-5: synchronous hard delete, tombstoned audit identifiers, 35-day backup horizon with restore re-deletion). Engine is resolved: PostgreSQL with Drizzle ORM and drizzle-kit (see Data model expectations; CLAUDE.md, Repository state). Data residency is resolved (SECURITY.md SQ-1: single US primary region); replication is RDS Multi-AZ within that region (SQ-7 RESOLVED) — cross-region replication would be a new decision.

- **AI Inference (in-boundary)**
  - **Responsibility:** Estimate calories and macronutrients from a subscriber-supplied food description or photo (FR-8.12), using a model that runs inside the system's cloud boundary — a managed in-account model service configured for zero prompt retention and no training use, or self-hosted weights (FR-8.13). Returns structured estimates only; the inference context grants the model no tool, retrieval, or data access beyond the estimation task (SECURITY.md SEC-AI-2).
  - **Inputs:** Estimation requests from the REST API Application carrying a food description or a transient photo.
  - **Outputs:** Structured calorie and macronutrient estimates, schema-validated by the REST API Application before presentation (SEC-INPUT-1, FR-8.9).
  - **Data owned or accessed:** Owns no durable data. Photos are transient and never persisted or logged (SEC-AI-3).
  - **Open decisions:** None. The model service is resolved (SECURITY.md SQ-7): Amazon Bedrock in the system's account with zero-retention, no-training configuration; sizing rides with deployment.

**Trust boundaries.** Six: (1) between the Browser Client and the REST API Application — the client is untrusted, and all authorization and validation decisions are re-made server-side regardless of what the client sent; (2) between unauthenticated and authenticated request handling at Identity and Session Handling; (3) between the REST API Application and Relational Persistence, which accepts requests from no other origin; (4) between the CI/CD-and-IaC path and the production environment — the build and deploy pipeline can rewrite the system itself, so its identities and Terraform state are a distinct trust concern (SECURITY.md SEC-CICD-*, SEC-SECRET-3); (5) between the application and human operational access below it — operators and holders of persistence or backup credentials reach health data without traversing the REST API's enforcement point (SECURITY.md SEC-OPS-1, SEC-LOG-7, SQ-13); (6) between the REST API Application and AI Inference — inference runs in-account under zero-retention configuration, model output is untrusted input revalidated before use, and subscriber-supplied descriptions and photos are prompt-injection vectors (SECURITY.md SEC-AI-1, SEC-AI-2). Boundaries 4 and 5 were identified by the 2026-07-31 threat model (SECURITY.md, Threat Model); boundary 6 was added 2026-08-01 with the OQ-5 AI component. There is no external-system boundary: health data does not leave the system (FR-9.8) — outbound transactional email (SECURITY.md SEC-EXT-3) carries notices and single-use tokens only, never health data, and its threats are tracked by SECURITY.md's 2026-08-03 addendum. Role separation (subscriber / consultant / admin) and consultant engagement scoping are enforced inside the REST API Application, not at the network edge.

**Primary data flows.**
1. *Authentication:* Client → Identity and Session Handling → credential/passkey verification → session context returned to client; subsequent requests carry it.
2. *Plan browse and view:* Client → REST API → entitlement and publication checks → Persistence → plan content with citations and verification record → Client.
3. *Customization:* Client → REST API → entitlement check → copy of published plan written as a subscriber-owned record; published plan untouched.
4. *Progress logging:* Client → REST API → consent check, owner scoping, field validation → log entry written → audit entry written.
5. *Progress viewing:* Client → REST API → owner scoping → entry-level log history over the requested range, and for diet, logged intake compared against the selected plan's targets → audit entry written (FR-9.7, one per request) → Client.
6. *Admin publication:* Admin client → REST API → role check, citation-presence gate, verification record → plan published.
7. *Consultant access:* Consultant client → REST API → active-engagement check → scoped subscriber data → audit entry written.
8. *Data export and deletion:* Client → REST API → owner scoping and sensitive-operation authorization (fresh re-authentication, SECURITY.md SEC-AUTHN-7) → export streamed or hard deletion executed synchronously → audit entry written. Execution is synchronous (SECURITY.md SQ-5 RESOLVED); no export artifact exists, so SEC-DATA-6 remains moot.
9. *Out-of-band deletion (FR-9.11):* Unauthenticated request → REST API → address-control verification and account-detail match → pending deletion request recorded → notice sent through the mail interface (SEC-EXT-3) and surfaced in any live session → 14-day window, cancellable from any authenticated session → window expiry evaluated by a scheduled execution → FR-9.4 deletion executes → audit entry written.

**Note on DESIGN.md:** DESIGN.md targets WCAG 2.2 AA, which resolves REQUIREMENTS.md OQ-11. The client boundary is therefore treated as having a firm accessibility target, not an open one.

### Dependency Rules

- **DR-1** The Browser Client MUST depend on the REST API Application only, and only through its published REST interface. It MUST NOT reach Relational Persistence or Identity and Session Handling storage directly.
- **DR-2** No business rule may exist only in the Browser Client. Every authorization, entitlement, ownership, publication-gate, and validation rule MUST be enforced by the REST API Application, and client-side checks are duplicate convenience only. Server responses MUST carry enough structured detail (failing field, reason) for the client to present errors per DESIGN.md without re-deriving the rule.
- **DR-3** The REST API Application MUST NOT depend on the Browser Client, on client-supplied identity or role claims, or on client-supplied ownership assertions. Identity and role come from Identity and Session Handling; ownership comes from persisted state.
- **DR-4** Every business object has exactly one owning component — the REST API Application — and only that component may mutate it. Published plans are mutable only by admin-role operations; subscriber plan copies are mutable only by their owning subscriber or, under FR-11.6, by a consultant with an active engagement (REQUIREMENTS.md OQ-12 RESOLVED); log entries are mutable only by their owning subscriber.
- **DR-5** Relational Persistence MUST be reachable at runtime only from the REST API Application — including its scheduled executions (SEC-LOG-7 archival, deletion-ledger maintenance, FR-9.11 expiry) — and Identity and Session Handling. The only sanctioned paths outside them are the CI/CD migration-and-import path (trust boundary 4: drizzle-kit migrations and the FR-8.11 dataset import) and the SEC-OPS-1 break-glass process (trust boundary 5). It MUST NOT initiate calls outward, and it MUST NOT be shared with any component outside this system. *(Sanctioned paths enumerated 2026-08-03.)*
- **DR-6** Dependencies MUST flow in one direction — Client → API → Identity/Persistence — with no cycles. Internal modules of the REST API Application MUST likewise depend across documented interfaces without cycles.
- **DR-7** Should any external service ever be introduced, it MUST be reached only through an internally defined interface owned by the REST API Application, and no vendor-specific type, error, identifier, or behavior may propagate past that interface. Health data MUST NOT cross such an interface (FR-9.8).
- **DR-8** No component may depend on an unresolved decision in a way that hard-codes it. Framework, database engine, session transport, and deployment choices MUST sit behind the component interfaces described above so that resolving them does not change component responsibilities or data flows.
- **DR-9** Audit entry writing (FR-9.7, FR-11.4) MUST be a dependency of every health-data access path within the REST API Application, not an optional caller responsibility that individual paths may omit.
