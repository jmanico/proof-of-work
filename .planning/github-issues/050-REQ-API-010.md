## Requirement

- **Statement**: The REST API Application MUST validate every request body, query parameter, path parameter, and header against an explicit allow-list schema declaring type, format, range, and length before any business logic executes, MUST reject non-conforming requests rather than coerce them, and MUST neutralize prototype-polluting keys during JSON handling.
- **Rationale**: SEC-INPUT-1 requires allow-list validation at the boundary and rejection rather than coercion; SEC-INPUT-6 requires prototype-pollution-safe JSON handling in the Node.js runtime. The threat model records tampered client payloads (TM-T-1) and prototype pollution (TM-T-8) as the threats answered. Numeric range checks on log-entry schemas source their plausibility ranges from `REQUIREMENTS.md` FR-8.9's named constants (body weight 20–500 kg, body-measurement lengths 10–300 cm, body-fat percentage 2–75, workout load 0–600 kg, checked against the metric equivalent of the entered value).
- **Assumptions**: A single server-side entry point exists (`ARCHITECTURE.md`, REST API Application).
- **Out of Scope**: Field-level binding rules for writes (REQ-API-020); numeric log-entry validation semantics (REQ-PROGRESS-030); request size and rate limits (SEC-HTTP-5; REQ-API-050 — `SECURITY.md` SQ-3 RESOLVED); binary food-photo upload validation — magic-byte type checks, decoded-dimension caps, decompression-anomaly rejection, EXIF/GPS stripping (SEC-INPUT-7; REQ-FOOD-040); error response shape (REQ-API-040).
- **Design Traceability**: `DESIGN.md` — Core Components → Forms and validation, insofar as rejections must name the specific problem so the client can present it inline with a specific correction.
- **Architecture Traceability**: `ARCHITECTURE.md` — trust boundary 1; REST API Application ("the sole authority for business rules"); DR-2 (responses carry structured failing-field detail); DR-3.
- **Security Traceability**: SEC-INPUT-1, SEC-INPUT-6; supports SEC-TB-1, SEC-INPUT-5.

## Acceptance Criteria

1. **AC-01 — Expected behavior**: Given a request conforming to an operation's schema, when it is received, then validation passes and the handler receives only the declared, typed fields.
2. **AC-02 — Boundary or failure behavior**: Given a request with a wrongly typed, out-of-range, over-length, malformed, or undeclared field, when it is received, then the request is rejected before any business logic or persistence access, the response identifies the failing field without disclosing internal state, and no state change occurs.
3. **AC-03 — Prohibited behavior**: Given any input, when it is processed, then the application MUST NOT coerce a non-conforming value into a conforming one, MUST NOT act on an undeclared field, MUST NOT allow `__proto__`, `constructor`, or `prototype` keys to mutate any object prototype, and MUST NOT evaluate untrusted input as code.
4. **AC-04 — Additional criterion**: Given a route inventory, when the validation test runs, then every route is bound to a declared schema and no route accepts unvalidated input.

## Failure Behavior

- **On Invalid Input**: Reject with a client-error status, a structured body naming the failing field and the rule it violated (DR-2), and no protected state change.
- **On Authentication Failure**: N/A — validation ordering relative to authentication is at the implementer's discretion, but neither may be skipped.
- **On Authorization Failure**: N/A — handled by REQ-AUTHZ-010 and REQ-AUTHZ-020.
- **On Security-Decision Failure**: If a schema cannot be resolved for a route, the request MUST be denied (fail closed) rather than passed through unvalidated.
- **On External Dependency Failure**: N/A — no external dependency participates.
- **On System Error**: Roll back any partial work; return a generic error with a correlation identifier per SEC-ERR-1.
- **Logging / Audit**: Log validation rejections with route, rule violated, and correlation identifier. MUST NOT log field values that may contain health data, credentials, or tokens (SEC-LOG-3).
- **Alerting**: Threshold alerts route to the security lead as SEC-OPS-2 detection inputs (`SECURITY.md` SQ-3, SQ-11 RESOLVED).

## Test Strategy

- **Unit Tests**: Per-schema tests for type, format, range, length, missing required, and undeclared-field cases.
- **Integration Tests**: Boundary tests per route asserting rejection precedes persistence access.
- **Security Tests**: Fuzzing with malformed and out-of-range payloads; prototype-pollution payloads (`__proto__`, `constructor.prototype`) asserting no global object mutation; static analysis rule forbidding dynamic evaluation of request-derived values.
- **Compliance Tests / Evidence**: N/A
- **Acceptance-Criteria Traceability**: AC-01 and AC-02 — schema conformance suite; AC-03 — pollution and coercion negative suite plus the no-eval SAST rule; AC-04 — route inventory test.
- **Coverage Target**: Every route bound to a schema; positive and negative coverage for every declared field.
- **Required Test Environment**: HTTP test client and fuzzing harness driven from Vitest.

## Implementation Notes

- **Constraints**: Node.js runtime with TypeScript, Fastify, and npm workspaces (`CLAUDE.md`).
- **Prohibited Approaches**: Deny-list filtering; per-handler ad-hoc `if` checks as the primary control; silently dropping unknown fields instead of rejecting; trusting a client-side validation result.
- **Implementation Guidance**: Centralize validation so it is not repeated per endpoint (the `SECURITY.md` CODE_QUALITY_PROMPT resolution, SEC-AUTHZ-5 rationale). Keep the schema registry and the route table in one place so AC-04 is mechanically checkable. Express FR-8.9's plausibility ranges as named constants shared with the log-entry schemas rather than re-declared per schema.
- **AI Development Guidance**: `REF-PROMPT-NODE`, `REF-PROMPT-API`, `REF-PROMPT-QUALITY`; `CLAUDE.md`.
- **Required Human Review**: Security review of the validation layer and the route-to-schema binding.
- **Open Decisions**: None. Request size and rate limits are fixed (SEC-HTTP-5; `SECURITY.md` SQ-3 RESOLVED) and delivered by REQ-API-050.
