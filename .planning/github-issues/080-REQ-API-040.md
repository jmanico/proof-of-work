## Requirement

- **Statement**: Error responses MUST carry a generic message and a correlation identifier without stack traces, framework or database detail, or internal identifiers, while full diagnostics remain server-side; and internal, debug, and diagnostic endpoints MUST NOT be exposed in production.
- **Rationale**: SEC-ERR-1 and SEC-HTTP-6 state these rules. The threat model records health data leaking into error responses (TM-I-5) as high severity, and `DESIGN.md` requires user-facing error text that names the problem and the fix — which is only compatible with SEC-ERR-1 if the structured detail is limited to validation outcomes.
- **Assumptions**: Validation failures carry structured field-level detail per DR-2 and REQ-API-010; that detail is user-facing product behavior, not internal diagnostics.
- **Out of Scope**: Log retention and access control (SEC-LOG-5, blocked by SQ-8); alerting; rate-limit responses (SEC-HTTP-5, blocked by SQ-3).
- **Design Traceability**: `DESIGN.md` — Components → Form feedback and errors ("The message names the specific problem and how to fix it, not a generic failure"), reconciled here as: validation messages are specific about the user's input, system errors are generic.
- **Architecture Traceability**: `ARCHITECTURE.md` — REST API Application outputs ("validation and authorization errors carrying the specific failing field or reason"); DR-2.
- **Security Traceability**: SEC-ERR-1, SEC-HTTP-6; supports SEC-LOG-3, SEC-AUTHN-3, SEC-DATA-5.

## Acceptance Criteria

1. **AC-01 — Expected behavior**: Given an unhandled server fault, when a response is produced, then the body contains a generic message and a correlation identifier, and the server log holds the full diagnostic detail under that same identifier.
2. **AC-02 — Boundary or failure behavior**: Given a validation failure, when a response is produced, then it names the failing field and the rule violated (DR-2, `DESIGN.md`) and contains no stack trace, framework or database detail, internal identifier, or health value.
3. **AC-03 — Prohibited behavior**: Given any error response, when it is inspected, then it MUST NOT vary in a way that discloses internal structure or whether a resource or account exists beyond what REQ-AUTHZ-040 and SEC-AUTHN-3 permit, and no debug, diagnostic, or internal route may be routable in production.
4. **AC-04 — Additional criterion**: Given a fault occurring inside authentication or authorization logic, when it is handled, then the operation is denied rather than allowed, and the denial is logged (SEC-AUTHZ-7, `SECURITY.md` code-quality resolution).

## Failure Behavior

- **On Invalid Input**: Structured field-level rejection per REQ-API-010, with no internal detail.
- **On Authentication Failure**: A uniform response that does not reveal which factor failed or whether the account exists (SEC-AUTHN-3, REQ-AUTH-040).
- **On Authorization Failure**: Deny; the response MUST NOT disclose the existence of a resource the actor is not entitled to know about (REQ-AUTHZ-040).
- **On Security-Decision Failure**: Deny by default; an exception raised inside an authentication or authorization path MUST NOT be swallowed and MUST NOT result in a permit.
- **On External Dependency Failure**: Generic error plus correlation identifier; no driver, engine, or endpoint detail.
- **On System Error**: Roll back; return the generic error shape; retain diagnostics server-side only.
- **Logging / Audit**: Log fault detail with the correlation identifier, route, and actor identifier. MUST NOT log health values, credentials, tokens, or full personal records (SEC-LOG-3).
- **Alerting**: TO BE DECIDED — no alert condition, threshold, severity, or destination is defined in any source document.

## Test Strategy

- **Unit Tests**: Error handler maps each internal error class to the generic response shape; correlation identifier generation uses a cryptographically secure source where it is also used as a lookup capability (SEC-SECRET-4).
- **Integration Tests**: Fault-injection at the persistence, validation, and authorization layers asserting response shape and log contents.
- **Security Tests**: Assertion that no response body contains a stack trace, SQL fragment, file path, or internal identifier; production route inventory asserting no diagnostic route; differential-response check against SEC-AUTHN-3.
- **Compliance Tests / Evidence**: N/A
- **Acceptance-Criteria Traceability**: AC-01 — fault-injection suite; AC-02 — validation error shape suite; AC-03 — response-hygiene scan plus route inventory review; AC-04 — fail-closed authorization fault test.
- **Coverage Target**: Every error class and every route exercised.
- **Required Test Environment**: HTTP test client with fault injection; log capture. Test framework TO BE DECIDED.

## Implementation Notes

- **Constraints**: Node.js runtime; framework TO BE DECIDED. The error handler MUST be centralized so the route inventory test can be exhaustive.
- **Prohibited Approaches**: Returning exception messages verbatim; echoing the submitted value back in an error when it may be health data; leaving a debug route behind a guessable path or a feature flag defaulting to enabled; swallowing exceptions in authentication or authorization paths.
- **Implementation Guidance**: Treat the correlation identifier as the only bridge between the client-visible error and server diagnostics.
- **AI Development Guidance**: `REF-PROMPT-NODE`, `REF-PROMPT-API`, `REF-PROMPT-QUALITY`; `CLAUDE.md`.
- **Required Human Review**: Security review of the error handler and the production route inventory.
- **Open Decisions**: Alerting is undefined across all source documents; log retention is blocked by `SECURITY.md` SQ-8.
