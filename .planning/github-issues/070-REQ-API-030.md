## Requirement

- **Statement**: All database access MUST use parameterized queries or an equivalent mechanism that separates code from data, and query text MUST NOT be assembled by concatenating untrusted input.
- **Rationale**: SEC-INPUT-5 states the rule; the threat model rates SQL injection through any input-bearing endpoint (TM-T-2) as high severity against the boundary that holds all health data.
- **Assumptions**: Relational persistence is reached only from the REST API Application and Identity and Session Handling (DR-5, SEC-TB-2).
- **Out of Scope**: Choice of RDBMS engine, query layer, or migration tooling, all `TO BE DECIDED` (`CLAUDE.md`, `ARCHITECTURE.md`); schema design; network placement of the data tier (SEC-TB-2, SEC-CICD-3, blocked by SQ-7).
- **Design Traceability**: N/A
- **Architecture Traceability**: `ARCHITECTURE.md` — trust boundary 3 (REST API Application → Relational Persistence); DR-5; Relational Persistence responsibilities.
- **Security Traceability**: SEC-INPUT-5; supports SEC-TB-2, SEC-AUTHZ-2 (scoped queries), SEC-DATA-5.

## Acceptance Criteria

1. **AC-01 — Expected behavior**: Given any operation that reads or writes persistence, when the query executes, then all request-derived values are bound as parameters and the query text is static or assembled only from server-controlled identifiers.
2. **AC-02 — Boundary or failure behavior**: Given input containing quote characters, comment sequences, statement separators, or union constructs, when it reaches any input-bearing endpoint, then it is treated as a literal value, the query returns the same result shape as for benign input, and no additional statement executes.
3. **AC-03 — Prohibited behavior**: Given the codebase, when static analysis runs, then no query text is produced by concatenating or interpolating a request-derived value, and no dynamic identifier (table, column, sort key) is taken from client input without mapping through a server-side allow-list.
4. **AC-04 — Additional criterion**: Given a query that returns records owned by a subject, when it is built, then the ownership predicate is part of the query rather than a post-retrieval filter (SEC-AUTHZ-2).

## Failure Behavior

- **On Invalid Input**: Rejected upstream by REQ-API-010; values that reach the query layer are bound as data and never alter query structure.
- **On Authentication Failure**: N/A
- **On Authorization Failure**: N/A — handled by REQ-AUTHZ-020, which this issue supports by requiring in-query scoping.
- **On Security-Decision Failure**: If a scope predicate cannot be resolved for a query, the query MUST NOT execute (fail closed).
- **On External Dependency Failure**: On persistence unavailability or timeout, return a generic error with a correlation identifier; MUST NOT expose engine, driver, or query detail (SEC-ERR-1).
- **On System Error**: Roll back the transaction; leave no partially applied write.
- **Logging / Audit**: Log persistence errors with a correlation identifier and no query text containing values. Health-data reads and writes produce audit entries via REQ-AUDIT-020.
- **Alerting**: TO BE DECIDED — no thresholds are defined.

## Test Strategy

- **Unit Tests**: Query builders produce parameter placeholders for every request-derived value; allow-list mapping rejects an unmapped sort or filter identifier.
- **Integration Tests**: Round-trip tests against the chosen engine asserting literal handling of injection-shaped input.
- **Security Tests**: Injection suite over all input-bearing endpoints; static analysis rule forbidding dynamic query construction; a test that an ownership predicate is present in the emitted query.
- **Compliance Tests / Evidence**: N/A
- **Acceptance-Criteria Traceability**: AC-01 and AC-04 — query construction unit suite; AC-02 — injection suite; AC-03 — SAST rule with a deliberate failing fixture.
- **Coverage Target**: Every input-bearing endpoint exercised by the injection suite; every query path covered by the SAST rule.
- **Required Test Environment**: A running instance of the selected RDBMS engine — engine TO BE DECIDED (`CLAUDE.md`, `ARCHITECTURE.md`).

## Implementation Notes

- **Constraints**: RDBMS engine, query layer, and migration tooling are TO BE DECIDED (`CLAUDE.md`). This issue is implementable only once the engine and access layer are chosen; the rule itself is fixed regardless of the choice.
- **Prohibited Approaches**: String concatenation or template interpolation into query text; escaping untrusted input by hand; passing client-supplied column or table names through to the query; disabling parameterization for "dynamic" filters.
- **Implementation Guidance**: Confine persistence access to a single layer so the SAST rule can be scoped and exhaustive.
- **AI Development Guidance**: `REF-PROMPT-NODE`, `REF-PROMPT-QUALITY`; `CLAUDE.md`.
- **Required Human Review**: Security review of the persistence access layer.
- **Open Decisions**: RDBMS engine and query layer selection (`CLAUDE.md`, `ARCHITECTURE.md` — Relational Persistence open decisions). These do not change the required behavior but must be settled before implementation starts.
