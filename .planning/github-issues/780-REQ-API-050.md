## Requirement

- **Statement**: The REST API Application MUST size-limit request bodies, time-bound request handling, and enforce per-actor and per-endpoint rate limits at the `SECURITY.md` SQ-3 named-constant values — 1 MB JSON and 10 MB photo-upload bodies; 120 requests/minute per account on the authenticated API; 10 requests/minute per source on authentication endpoints; 5/minute burst and 50/day per account on AI estimation; one export per day per account — rejecting each violation with a non-descriptive error.
- **Rationale**: SEC-HTTP-5 (Confirmed) requires these limits, fixed by SQ-3 as named constants; threat TM-D-1 identifies resource exhaustion on the public surface amplified by expensive endpoints (export, history aggregation), and SEC-AI-2 identifies inference cost as a denial-of-wallet target requiring the 5/minute and 50/day thresholds. The export limit also bounds TM-I-7's exfiltration channel (SQ-5).
- **Assumptions**: Per-account limits key on the identity resolved from the server-side session (REQ-SESSION-030 via REQ-AUTHZ-010); per-source limits key on the request source as seen at the API behind CloudFront and the ALB (SQ-7 topology). Throttle and quota counters are the persisted entity `ARCHITECTURE.md` names, so limits hold across concurrent ECS Fargate tasks and task restarts.
- **Out of Scope**: Exponential backoff on failed authentication attempts keyed per account and per source (SEC-AUTHN-6 — REQ-AUTH-060; the 10/minute per-source cap here is additional to it); email-verification resend limits (SEC-AUTHN-8 — its issue); HSTS and security response headers (SEC-HTTP-1, SEC-HTTP-2 — REQ-PLATFORM-040); food-photo content validation beyond size (SEC-INPUT-7 — REQ-FOOD-040); infrastructure-level DDoS absorption, which no spec document assigns to the application.
- **Design Traceability**: N/A — `DESIGN.md` does not present rate limiting; the generic system-failure presentation with a correlation identifier (Forms and validation) applies to the client rendering of a rejection.
- **Architecture Traceability**: `ARCHITECTURE.md` — Data model expectations: "throttle and quota counters (SECURITY.md SEC-AUTHN-6, SEC-HTTP-5)" as a persisted entity; REST API Application as the single server-side entry point; deployment on ECS Fargate with multiple tasks (SQ-7) motivating shared counters.
- **Security Traceability**: SEC-HTTP-5; SEC-AI-2 (inference thresholds); SEC-ERR-1 (non-descriptive rejection); SEC-AUTHN-6 boundary (the per-source authentication cap complements backoff); SEC-DATA-3/SQ-5 (export once per day).

## Security Context

- **Security Objectives**: Availability, Confidentiality
- **Control Layers**: Availability, Input Validation, Architecture
- **Threat References**: `SECURITY.md` TM-D-1 (resource exhaustion amplified by expensive endpoints), TM-I-7 (export as exfiltration channel, bounded by the daily limit), SEC-AI-2 denial-of-wallet; CWE-770 (allocation of resources without limits or throttling), CWE-400 (uncontrolled resource consumption), CWE-405 (asymmetric resource consumption)
- **Abuse / Misuse Case**: An attacker floods authentication endpoints from one source; an authenticated account hammers history aggregation or drives inference cost with rapid estimation calls; an oversized or slow-trickled body ties up a task; a stolen session bulk-pulls exports; an attacker distributes load across Fargate tasks expecting per-task counters to under-count.
- **Trust Boundary**: Boundary 1 — request volume, body size, and duration are attacker-controlled properties of untrusted traffic.
- **Untrusted Inputs or Assertions**: Request bodies and their declared and actual sizes; request rates; any client-supplied source or identity signal not derived from the session or the trusted network path.
- **Authoritative Enforcement Point**: REST API Application — limits evaluated in the request pipeline before handler execution, against counters in Relational Persistence shared by all tasks.
- **Independent Verification**: The per-account key comes from the server-side session record, never a client claim (DR-3); body size is enforced on actual received bytes, not the `Content-Length` assertion alone.
- **Zero Trust Relevance**: N/A — this is an availability control, not a resource-access decision; NIST SP 800-207 is not stretched to cover it.

## Acceptance Criteria

1. **AC-01 — Expected behavior**: Given traffic within every limit, when requests arrive, then they proceed unaffected; and each limit — 1 MB JSON body, 10 MB photo body, 120/minute per account, 10/minute per source on authentication endpoints, 5/minute burst and 50/day per account on AI estimation, one export per day per account — is defined once as a named constant matching the SQ-3 values.
2. **AC-02 — Boundary or failure behavior**: Given a request exceeding any limit — a JSON body over 1 MB, a photo upload over 10 MB, the 121st API request in a minute for an account, the 11th authentication request in a minute from a source, the 6th estimation request in a minute or the 51st in a day for an account, or a second export in a day — when it is processed, then it is rejected before handler execution with a non-descriptive error carrying a correlation identifier and no internal detail (SEC-ERR-1), and no protected state changes.
3. **AC-03 — Boundary or failure behavior**: Given a request whose handling exceeds the time bound (including a slow-trickled request body), when the bound elapses, then handling is terminated and the connection resolved with a generic error, without leaving the task wedged; and given the same account's traffic spread across multiple concurrent API tasks, when the aggregate exceeds a limit, then it is rejected — counters are shared, not per-process.
4. **AC-04 — Prohibited behavior**: Given a rejected request, when the response is produced, then it MUST NOT disclose remaining quota, reset time, counter internals, or whether the keyed account exists (SEC-AUTHN-3 on authentication endpoints); and a body MUST NOT be buffered past its size limit before rejection.

## Failure Behavior

- **On Invalid Input**: Oversized bodies are rejected at the size limit as received, without full buffering; schema validation of in-limit bodies remains REQ-API-010's concern.
- **On Authentication Failure**: N/A for the per-source limit, which applies before and regardless of authentication; authentication-failure responses themselves are REQ-AUTH-010/REQ-AUTH-060 behavior.
- **On Authorization Failure**: N/A — limits are evaluated alongside, not instead of, the authorization pipeline; a throttled request never reaches authorization.
- **On Security-Decision Failure**: Deny by default: if a counter cannot be read or written, the limited operation on expensive endpoints (AI estimation, export) is refused rather than allowed uncounted; an error inside limit evaluation MUST NOT admit the request.
- **On External Dependency Failure**: N/A — counters live in Relational Persistence; its unavailability fails the request generically.
- **On System Error**: Generic error with correlation identifier (SEC-ERR-1); counters remain consistent — a failed request MAY still consume quota, and that bias toward denial is acceptable.
- **Logging / Audit**: Each rejection logs route, limit class, keyed identifier (account identifier or source), and correlation identifier (SEC-LOG-4 context for attack-pattern detection); logs never contain credentials, tokens, or health values (SEC-LOG-3).
- **Alerting**: Threshold alerts on sustained limit violations route to the security lead as SEC-OPS-2 detection inputs (`SECURITY.md` SQ-3, SQ-11 RESOLVED).

## Test Strategy

- **Unit Tests**: Named-constant values match SQ-3; window and quota arithmetic (minute windows, daily quotas, burst versus daily interaction on estimation); key derivation from session identity and source; fail-closed behavior when counter storage errors.
- **Integration Tests**: Burst tests per limit class asserting the boundary request passes and the next is rejected; oversized JSON and photo uploads asserting early rejection; two API task instances sharing one counter store asserting aggregate enforcement; time-bound test with a deliberately slow handler and a slow-trickled body.
- **Security Tests**: Response-content review of rejections asserting no quota, reset, existence, or internal disclosure; distributed-source probes on authentication endpoints; denial-of-wallet simulation against the estimation endpoint asserting the 5/minute and 50/day caps hold; export-limit test asserting the second same-day export is refused (TM-I-7).
- **Compliance Tests / Evidence**: N/A — no regulation names these thresholds; the SQ-3 resolution is the internal authority.
- **Acceptance-Criteria Traceability**: AC-01 — named-constant unit suite plus pass-through integration tests; AC-02 — per-limit burst and oversize suites; AC-03 — time-bound and multi-task suites; AC-04 — rejection-content review tests.
- **Coverage Target**: Project coverage threshold is 90% line and branch (`CLAUDE.md`, 2026-08-03); every limit class MUST have a passing-boundary and rejected-boundary test.
- **Required Test Environment**: Vitest; HTTP test client; two concurrently running API instances against one PostgreSQL counter store; fixture accounts and distinct source addresses; a clock control for window and daily-quota rollover.

## Implementation Notes

- **Constraints**: TypeScript on Node.js with Fastify (`CLAUDE.md`); limits as named constants with the SQ-3 values (the `SECURITY.md` CODE_QUALITY_PROMPT resolution's named-constant discipline); counters persisted in the `ARCHITECTURE.md` throttle-and-quota entity so enforcement is aggregate across Fargate tasks; enforcement in the request pipeline before handlers.
- **Prohibited Approaches**: In-memory per-process counters as the enforcement mechanism; trusting `Content-Length` without enforcing received bytes; descriptive rejection bodies revealing quota state or account existence; introducing an external rate-limiting service (no external integration without SEC-EXT-1 change); exempting internal or admin routes from the per-account limit without a documented decision; treating rate limiting as a substitute for SEC-AUTHN-6 backoff.
- **Implementation Guidance**: Fastify's body-limit configuration covers the size caps per content type; register limit checks as early request-pipeline hooks so rejected traffic spends minimal compute. Keep counter reads and increments atomic in PostgreSQL (single-statement upsert) to avoid race under-counting; a fixed- or sliding-window design is acceptable so long as the named constants are honored at the boundary values. Export and estimation quotas are daily per account and survive restarts by construction in persistence. Coordinate with REQ-AUTH-060 so authentication endpoints carry both controls: this issue's flat 10/minute per source and SEC-AUTHN-6's exponential backoff.
- **AI Development Guidance**: `REF-PROMPT-API`, `REF-PROMPT-NODE`, `REF-PROMPT-QUALITY`; `CLAUDE.md`.
- **Required Human Review**: Security review of the limit constants against SQ-3, the counter atomicity, and the rejection-response content.
- **Open Decisions**: None — SQ-3 fixed every threshold; alert routing is fixed by SQ-11.
