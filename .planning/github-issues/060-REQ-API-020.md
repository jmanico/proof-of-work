## Requirement

- **Statement**: Every create and update operation MUST bind only an explicit allow-list of client-assignable fields, and the server-controlled fields — owner identity, role, subscription state, engagement state, publication status, verification record, and audit fields — MUST NOT be settable from a request body.
- **Rationale**: SEC-INPUT-3 states the rule verbatim. Without it, a subscriber could self-assign a role, mark a plan published, forge a verification record, or reassign ownership, defeating FR-4.5, FR-7.2, FR-9.1, FR-10.1, and the entitlement rules.
- **Assumptions**: All writes traverse the REST API Application (DR-4).
- **Out of Scope**: Schema-level type validation (REQ-API-010); who may perform an operation at all (REQ-AUTHZ-010, REQ-AUTHZ-020, REQ-AUTHZ-030); role provisioning and lifecycle, which `SECURITY.md` SQ-12 leaves open.
- **Design Traceability**: N/A — `DESIGN.md` does not address request binding.
- **Architecture Traceability**: `ARCHITECTURE.md` — DR-3 ("MUST NOT depend on client-supplied identity or role claims, or on client-supplied ownership assertions"); DR-4; REST API Application responsibilities.
- **Security Traceability**: SEC-INPUT-3; supports SEC-TB-1, SEC-AUTHZ-1, SEC-AUTHZ-8, SEC-INPUT-4.

## Acceptance Criteria

1. **AC-01 — Expected behavior**: Given a create or update request containing only client-assignable fields, when it is processed, then exactly those fields are persisted and every server-controlled field is set from session context or server logic.
2. **AC-02 — Boundary or failure behavior**: Given a request that additionally contains `role`, owner identity, subscription state, engagement state, publication status, a verification record, or an audit field, when it is processed, then those fields are ignored or the request is rejected, and the persisted record shows the server-derived values unchanged.
3. **AC-03 — Prohibited behavior**: Given any write path, when it constructs a persistence payload, then it MUST NOT pass a raw request body or a whole-object spread into persistence, and MUST NOT derive owner identity from the request.
4. **AC-04 — Additional criterion**: Given an update to an object the actor owns, when the request omits a field, then the omitted field is left unchanged and is not reset to a default.

## Failure Behavior

- **On Invalid Input**: Reject or ignore the prohibited field per the operation's declared binding, with no protected state change; the response names the rejected field without exposing internal schema detail.
- **On Authentication Failure**: N/A — handled upstream by REQ-AUTHZ-010.
- **On Authorization Failure**: Deny the operation; do not disclose whether the target record exists beyond what REQ-AUTHZ-020 permits.
- **On Security-Decision Failure**: If the binding allow-list for an operation cannot be resolved, deny the write (fail closed).
- **On External Dependency Failure**: N/A
- **On System Error**: Roll back the write transaction; return a generic error with a correlation identifier (SEC-ERR-1).
- **Logging / Audit**: Log attempts to set a server-controlled field with actor, operation, and field name — never the value if it may contain personal or health data (SEC-LOG-3). Health-data writes additionally produce an audit entry via REQ-AUDIT-020.
- **Alerting**: TO BE DECIDED — no thresholds are defined.

## Test Strategy

- **Unit Tests**: Binding function for each operation returns only allow-listed keys given an adversarial superset payload.
- **Integration Tests**: End-to-end write with an over-broad payload, asserting persisted state matches the server-derived values.
- **Security Tests**: Mass-assignment suite per write operation submitting each prohibited field; a privilege-escalation test submitting `role` on a self-update; an ownership-reassignment test submitting a foreign owner identifier.
- **Compliance Tests / Evidence**: N/A
- **Acceptance-Criteria Traceability**: AC-01 and AC-04 — binding unit suite; AC-02 and AC-03 — mass-assignment security suite plus a static check for whole-object spreads into persistence.
- **Coverage Target**: Every create and update operation covered by a positive and a mass-assignment negative test.
- **Required Test Environment**: HTTP test client with fixtures for each role; test framework TO BE DECIDED.

## Implementation Notes

- **Constraints**: Node.js runtime; ORM or query layer TO BE DECIDED (`CLAUDE.md`).
- **Prohibited Approaches**: Deny-lists of forbidden fields; passing `req.body` into a persistence call; deriving owner identity from a client-supplied field or header (DR-3).
- **Implementation Guidance**: Express the allow-list next to the operation's input schema from REQ-API-010 so a new field cannot be added in one place and silently bound in the other.
- **AI Development Guidance**: `REF-PROMPT-API`, `REF-PROMPT-QUALITY`; `CLAUDE.md`.
- **Required Human Review**: Security review of every binding allow-list.
- **Open Decisions**: Role assignment and provisioning remain open (`SECURITY.md` SQ-12); this issue only guarantees that role is never client-assignable, which is normative independently of how roles are assigned.
