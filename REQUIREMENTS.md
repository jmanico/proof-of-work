# Required Requirement Inputs

- **Project purpose:** A fitness web application that delivers science-based, admin-curated exercise and diet plans, lets users customize those plans, and tracks their progress over time. Access requires a paid subscription.
- **Primary users / actors:** Subscriber (registered end user who follows plans and logs progress); Fitness consultant / helper (available to subscribers as a paid option); Admin (authors, cites, verifies, and publishes plan content)
- **Core workflows:** Register and authenticate; subscribe; browse and select an exercise or diet plan; customize a plan into a personal copy; log workouts, food intake, weight, and measurements; view progress over time; admin authors and verifies plans
- **Business objects / data entities:** User account; subscription; exercise plan (with cited sources); diet plan (meals, calorie/macro targets, cited sources); user plan copy (customized); workout log entry; food log entry; body weight entry; body measurement entry
- **External integrations:** None at runtime beyond in-boundary AWS services — the system is self-contained. The bundled nutrition dataset (FR-8.11) is imported at build or deploy time; AI inference for nutrition estimation runs on infrastructure inside the system's own cloud boundary (FR-8.13); transactional email (verification, password reset, privileged invitations, deletion notices) is sent through an in-account email service and carries no health data (SECURITY.md SEC-EXT-3, 2026-08-03); no third-party application service receives user data
- **Authentication / roles:** Account required. Subscribers authenticate with standard consumer authentication: email + password minimum, with optional user-enabled MFA. Admins and fitness consultants MUST authenticate with a passkey. Roles: subscriber, consultant, admin
- **Regulatory or privacy constraints:** US consumer-health laws apply to user health data — the FTC Health Breach Notification Rule, state consumer-health laws (e.g. Washington My Health My Data), and CCPA/CPRA; HIPAA is not applicable because no covered-entity or business-associate relationship exists (OQ-3 RESOLVED; SECURITY.md SQ-1); GDPR and UK GDPR govern EU/UK data subjects, and GDPR-grade data-subject rights are granted to all users; a medical disclaimer stating the content is not medical advice must be shown

# Functional Requirements

### Delivery Channel

- **FR-1.1** The system MUST be delivered as a web application accessible through current desktop and mobile web browsers.
- **FR-1.2** The system MUST present a usable, responsive layout at both desktop and mobile viewport sizes, with no loss of function or content on mobile.

### Accounts and Authentication

- **FR-2.1** The system MUST require a user account for all plan, customization, and progress functionality, and MUST deny unauthenticated access to those functions.
- **FR-2.2** The system MUST allow a user to register an account with an email address and a password.
- **FR-2.3** The system MUST allow a registered user to authenticate with email and password, and MUST reject invalid credentials without revealing which factor was wrong.
- **FR-2.4** The system MUST allow a user to end their session (log out).
- **FR-2.5** The system MUST allow a user to enable and disable multi-factor authentication on their own account. MFA MUST be optional, not required.
- **FR-2.6** When MFA is enabled for an account, the system MUST require a successful second factor before granting an authenticated session.
- **FR-2.7** The system MUST assign every account exactly one of the roles `subscriber`, `consultant`, or `admin`.
- **FR-2.8** The system MUST require passkey authentication for accounts with the `admin` or `consultant` role, and MUST NOT allow those accounts to authenticate with a password alone.
- **FR-2.9** The system MUST allow an `admin` or `consultant` account to register a passkey and to register a replacement passkey.
- **FR-2.10** The system MUST create `admin` and `consultant` accounts only through an invitation issued by an existing `admin`, MUST allow the invited person to register their first passkey through that invitation, and MUST NOT allow a role to be selected or changed by the account holder. The first `admin` account is created by a one-time out-of-band provisioning step that is unavailable once an `admin` exists. *(SECURITY.md SEC-AUTHN-9; threats TM-S-4, TM-E-1.)*
- **FR-2.11** The system MUST require a user to verify control of the email address they registered, and MUST refuse to record health data (FR-9.12) for an account whose address is not yet verified. An unverified account MAY otherwise exist and authenticate. *(SECURITY.md SEC-AUTHN-8; threat TM-S-3.)*
- **FR-2.12** The system MUST allow a subscriber to reset a forgotten password using a single-use, time-limited token sent to their verified email address. Completing a reset MUST NOT satisfy, disable, or bypass an enabled second factor, and MUST terminate all of that account's existing sessions. *(SECURITY.md SEC-AUTHN-10, SEC-AUTHN-12; threat TM-S-2.)*
- **FR-2.13** The system MUST issue single-use recovery codes when a subscriber enables MFA, MUST present them exactly once, and MUST accept one in place of the second factor. The system MUST NOT provide any other route to bypass an enabled second factor, and no `admin` may clear or reset a subscriber's MFA. *(SECURITY.md SEC-AUTHN-10, SEC-AUTHN-11; threat TM-S-2.)*
- **FR-2.14** The system MUST state, before a subscriber enables MFA, that losing every factor and every recovery code makes the account permanently unrecoverable. *(This is a deliberate trade of recoverability for health-data protection; its tension with FR-9.3 and FR-9.5 is resolved in OQ-17 — an out-of-band deletion channel, FR-9.11.)*
- **FR-2.15** The system MUST enforce a two-passkey floor on every `admin` and `consultant` account at two defined moments: while fewer than two passkeys are registered, the account operates but MUST be shown a persistent prompt to register the second (a newly invited account necessarily starts with one — DESIGN.md, Passkeys); and a passkey removal or replacement that would leave fewer than two registered passkeys MUST be refused. The system MUST maintain at least two `admin` accounts, and MUST recover a privileged account that has lost passkey access only by a fresh invitation from another `admin` under FR-2.10. No password or email-possession path may restore privileged access. *(SECURITY.md SEC-AUTHN-2, SEC-AUTHN-9, SEC-AUTHN-10; threats TM-S-2, TM-S-4; enforcement moments fixed 2026-08-03, aligning with DESIGN.md's non-blocking callout.)*
- **FR-2.16** The system MUST record, on every `admin` and `consultant` invitation, who vetted the invitee, when, and on what basis, and MUST refuse to issue an invitation without that record. Vetting itself — identity and fitness-credential checks — happens out of band by the operator; the record makes it auditable. *(Resolves the vetting half of OQ-13 and SECURITY.md SQ-12; SEC-AUTHN-9, SEC-LOG-4.)*
- **FR-2.17** The system MUST allow an `admin` to deprovision any `admin` or `consultant` account: the account is disabled, all of its sessions are terminated immediately, its registered passkeys are invalidated, and for a consultant every active engagement is ended with access revoked per FR-11.3. Deprovisioning MUST produce an audit entry, MUST be refused when it would leave fewer than two `admin` accounts (FR-2.15), and a deprovisioned account MUST NOT be re-enabled except by a fresh invitation under FR-2.10. *(Resolves the deprovisioning half of SECURITY.md SQ-12; SEC-AUTHN-13.)*
- **FR-2.18** The system MUST allow a user to change their registered email address. The change MUST require fresh re-authentication (SECURITY.md SEC-AUTHN-7), MUST verify control of the new address before it replaces the old — the old address remains authoritative for recovery until verification completes — MUST send notice of the change to the previous address, MUST terminate all existing sessions on completion (SEC-AUTHN-12), MUST produce an audit entry, and MUST be refused while an FR-9.11 deletion request is pending. *(Added 2026-08-03: FR-9.5's correction right extends to the registered address, which is also the recovery anchor.)*

### Subscription and Access Control

- **FR-3.1** The system MUST require an active subscription for a subscriber to access exercise plans, diet plans, customization, and progress tracking.
- **FR-3.2** The system MUST deny plan and progress-tracking access to authenticated users without an active subscription, and MUST tell them a subscription is required.
- **FR-3.3** The system MUST allow a user to view their current subscription status.
- **FR-3.4** The system MUST retain a user's existing progress records and plan customizations when their subscription lapses, and MUST restore access to them when the subscription becomes active again.
- **FR-3.5** The system MUST allow an `admin` to grant, extend, and revoke a subscription period on a subscriber account, and MUST record an audit entry for each such action capturing the acting admin, the affected account, the action, the period bounds, and the time. *(Resolves OQ-1; SECURITY.md SEC-AUTHZ-8, threat TM-E-4.)*
- **FR-3.6** The system MUST treat a subscription as active exactly when the current time falls within a granted period on the account, and MUST NOT provide any other mechanism that activates a subscription. Payment collection occurs out of band in v1 (OQ-1, OQ-18).

### Plan Library and Content Verification

- **FR-4.1** The system MUST provide a library of exercise plans and diet plans authored by admins.
- **FR-4.2** The system MUST NOT allow subscribers to author plans, submit plans for publication, or share plans with other users.
- **FR-4.3** The system MUST allow an admin to create, edit, publish, and unpublish plans.
- **FR-4.4** The system MUST require every plan to carry at least one citation to a peer-reviewed source before it can be published, and MUST block publication of a plan with no citation.
- **FR-4.5** The system MUST require explicit admin verification of a plan before publication, and MUST record which admin verified it and when.
- **FR-4.6** The system MUST display a plan's citations to the user when the plan is viewed.
- **FR-4.7** The system MUST show only published plans to subscribers.
- **FR-4.8** Verification under FR-4.5 is a one-time gate: it is required once, before first publication, and MAY be performed by any `admin`, including the plan's author. An edit to a published plan MUST NOT clear or re-require verification, and MUST be rejected if it would leave the plan without at least one citation (FR-4.4). *(Resolves OQ-10 and OQ-16; SECURITY.md TM-T-5 risk accepted.)*
- **FR-4.9** Unpublishing a plan MUST end every active selection (FR-5.3, FR-6.4) that names it: each affected subscriber is shown an explanatory state and prompted to select a replacement, no logged history is altered, and the FR-8.5 comparison presents its no-target state until a new diet plan is selected. Unpublication MUST NOT alter customized copies (FR-7.5). *(Added 2026-08-03: resolves the unpublish-while-selected gap.)*

### Exercise Plans

- **FR-5.1** The system MUST allow a subscriber to browse published exercise plans and view a plan's full contents, including its exercises and prescribed sets and repetitions.
- **FR-5.2** The system MUST allow a subscriber to select an exercise plan to follow.
- **FR-5.3** The system MUST maintain at most one active exercise plan selection per subscriber, where the selection names either a published exercise plan or one of the subscriber's own customized exercise plan copies; selecting another MUST replace the current selection, and neither selection nor replacement may alter any logged history. *(Resolves OQ-6.)*
- **FR-5.4** The system MUST maintain an admin-curated exercise catalog: each exercise is a first-class record with a stable identifier and a name. Exercise plans and customized exercise plan copies MUST compose their exercises by referencing catalog entries — customization selects among catalog exercises and edits prescriptions (sets, repetitions, order), and MUST NOT introduce movements outside the catalog. A catalog entry MUST NOT be deleted once referenced by any plan, copy, or log entry; it MAY be retired from new use, and renaming it MUST NOT change its identifier. Catalog create, edit, and retire actions are restricted to `admin` accounts and MUST produce audit entries per FR-10.2. *(Added 2026-08-03: gives FR-8.14 per-exercise trends a stable identity across plans, copies, and renames.)*

### Diet Plans

- **FR-6.1** The system MUST allow a subscriber to browse published diet plans and view a plan's full contents.
- **FR-6.2** Each diet plan MUST specify its meals and its daily calorie and macronutrient targets. The macronutrients are protein, carbohydrate, and fat, each targeted in grams; this trio is the system-wide macronutrient set (FR-8.4, FR-8.5, FR-8.12). *(Macronutrient set resolved 2026-08-03.)*
- **FR-6.3** The system MUST allow a subscriber to select a diet plan to follow.
- **FR-6.4** The system MUST maintain at most one active diet plan selection per subscriber, where the selection names either a published diet plan or one of the subscriber's own customized diet plan copies; selecting another MUST replace the current selection, and neither selection nor replacement may alter any logged history. The FR-8.5 target comparison uses the currently selected diet plan. *(Resolves OQ-6.)*

### Plan Customization

- **FR-7.1** The system MUST allow a subscriber to customize a published exercise or diet plan by editing its contents.
- **FR-7.2** The system MUST save a customization as a private copy owned by that subscriber, and MUST NOT modify the published plan.
- **FR-7.3** The system MUST persist a subscriber's customized plans across sessions and MUST make them retrievable by that subscriber.
- **FR-7.4** The system MUST NOT allow a subscriber to view or modify another subscriber's customized plans.
- **FR-7.5** The system MUST preserve an existing customized copy unchanged when the published plan it was derived from is later edited or unpublished.

### Progress Tracking

- **FR-8.1** The system MUST allow a subscriber to log a body weight entry with a date.
- **FR-8.2** The system MUST allow a subscriber to log body measurement entries with a date. The measurement fields are waist, chest, hips, upper arm, and thigh — each a length in the account's unit system (FR-8.10) — and body-fat percentage, which is unitless and MUST be within 0–100. Every field is optional per entry, an entry MUST carry at least one value, and each field holds a single value — no left/right laterality in v1. *(OQ-4 RESOLVED; per-entry optionality resolved 2026-08-03.)*
- **FR-8.3** The system MUST allow a subscriber to record completion of a workout from their plan, including sets, repetitions, and weight used per exercise. Each logged exercise MUST reference its catalog entry (FR-5.4) and MUST store a snapshot of the exercise name at log time, so later catalog renames never alter logged history. *(Catalog reference added 2026-08-03.)*
- **FR-8.4** The system MUST allow a subscriber to log food intake and MUST attribute calories and the FR-6.2 macronutrients — protein, carbohydrate, and fat — to each logged entry.
- **FR-8.5** The system MUST display logged calories and macronutrients for a given day against the targets of the subscriber's selected diet plan.
- **FR-8.6** The system MUST display a subscriber's logged history over time for body weight, body measurements, and workout performance.
- **FR-8.7** The system MUST allow a subscriber to edit and delete their own log entries.
- **FR-8.8** The system MUST allow a subscriber to log entries for a past date, not only the current date. Entries dated in the future MUST be rejected (FR-8.9). *(Future-date rule resolved 2026-08-03.)*
- **FR-8.9** The system MUST reject log entries with a non-numeric, negative, absent-required, future-dated, or out-of-range value and MUST report the specific invalid field to the user. Plausibility ranges are named constants, checked against the metric equivalent of the entered value: body weight 20–500 kg; body-measurement lengths 10–300 cm; body-fat percentage 2–75 (within FR-8.2's 0–100 bound); workout load 0–600 kg; sets per exercise 1–100 and repetitions per set 1–1000, both integers. An entry date is future-dated when it is later than the current calendar date evaluated at UTC+14 — the earliest civil timezone, a named constant — so a legitimate "today" is never rejected for any user's local timezone and no per-account timezone field is required. Weights and lengths are stored to at most one decimal place. *(Ranges, precision, and the out-of-range class resolved 2026-08-03; sets/repetitions bounds and the future-date clock fixed 2026-08-03; SECURITY.md SEC-INPUT-1's range checks source from here.)*
- **FR-8.10** The system MUST maintain a per-account unit-system preference — metric (centimetres, kilograms) or imperial (inches, pounds) — applied to body measurements, body weight, and workout load; MUST store every logged value together with the unit it was entered in; and MUST convert between unit systems only at display time, never by mutating stored values. *(Resolves OQ-4 together with DESIGN.md OQ-8's unit half.)*
- **FR-8.11** The system MUST bundle a nutrition dataset imported into its own persistence at build or deploy time — initially USDA FoodData Central — MUST record the dataset version in use, MUST allow a subscriber to create a food log entry by searching the dataset and choosing a quantity, and MUST NOT issue runtime requests to any external nutrition service. Values computed from a dataset item are stored on the entry itself, so later dataset updates never alter logged history. *(Resolves OQ-5 together with FR-8.12 and FR-8.13.)*
- **FR-8.12** The system MUST offer AI-assisted estimation of calories and macronutrients from a subscriber-supplied food description or photo. The estimate MUST be presented as an editable pre-fill that the subscriber confirms before the entry is saved — typing values directly with no estimate requested is the same path — MUST be validated per FR-8.9 on save, and an entry created from an estimate MUST be labelled as an estimate. An estimation request is itself collection and processing of health data (FR-9.12): the system MUST refuse it for an account without recorded consent (FR-9.2), with consent withdrawn (FR-9.9), or with an unverified email address (FR-2.11). *(Consent gating resolved 2026-08-03.)*
- **FR-8.13** AI inference for FR-8.12 MUST execute only within the system's own cloud boundary — a managed model service in the system's account configured for zero prompt retention and no training use, or self-hosted model weights — MUST NOT transmit user data to any third-party application service (FR-9.8), and MUST process food photos transiently, never persisting or logging them; only the description and the confirmed values are stored. *(SECURITY.md SEC-AI-1–SEC-AI-3.)*
- **FR-8.14** The system MUST retain and display progress history at full entry granularity for the lifetime of the account, MUST present body weight, each body-measurement field, and per-exercise workout load as trend charts over selectable ranges of 4 weeks, 3 months, 1 year, and all time, and MUST pair every chart with an accessible data table presenting the same data. Per-exercise means per catalog entry (FR-5.4), so trends continue across plan switches, copies, and renames; the charted load value is the top-set weight — the heaviest weight logged for that exercise in the session, in the account's unit system (FR-8.10) — and the paired table shows the full sets, repetitions, and weight. *(Resolves OQ-7 and DESIGN.md OQ-4; exercise identity and chart metric resolved 2026-08-03.)*

### Data Rights, Privacy, and Safety

- **FR-9.1** The system MUST scope every plan copy and log entry to its owning subscriber, and MUST NOT expose one subscriber's data to another subscriber.
- **FR-9.2** The system MUST obtain the user's explicit consent to collect and process their health data before any health data (FR-9.12) is recorded or any AI estimation request is accepted (FR-8.12).
- **FR-9.3** The system MUST allow a user to export all of their own account, plan, and progress data in a machine-readable form, delivered synchronously as a single JSON download over the authenticated session; no export artifact is stored. Export is a sensitive operation requiring fresh re-authentication (SECURITY.md SEC-AUTHN-7) and produces one audit entry per export. *(SECURITY.md SQ-5 RESOLVED; re-authentication and audit granularity resolved 2026-08-03.)*
- **FR-9.4** The system MUST allow a user to request deletion of their account and all associated personal and health data, and MUST complete the deletion: live-system deletion is a synchronous hard delete effective at execution time — execution is immediate for an authenticated request, and follows the 14-day window for an FR-9.11 request — and full completion, including expiry of backup copies, occurs within 35 days of execution. In-session deletion is a sensitive operation requiring fresh re-authentication (SECURITY.md SEC-AUTHN-7). Deletion of an `admin` account MUST be refused while it would leave fewer than two `admin` accounts (FR-2.15) — a replacement is provisioned, or the account deprovisioned under FR-2.17, first; deletion of a `consultant` account first ends its active engagements with access revoked per FR-11.3. Any backup restore MUST re-apply deletions performed since that backup, driven by the deletion ledger (SECURITY.md SEC-DATA-4). *(SECURITY.md SQ-5 RESOLVED; execution clock, re-authentication, privileged floor, and ledger resolved 2026-08-03.)*
- **FR-9.5** The system MUST allow a user to view and correct the personal data held about them.
- **FR-9.6** The system MUST display a disclaimer stating that the plans and content are not medical advice, and MUST require the user to acknowledge it before they first use a plan.
- **FR-9.7** The system MUST record an audit entry for each access to or modification of a user's health data — including the user's own reads — capturing the acting account, the action, the affected subject, and the time. Granularity is one audit entry per request; an FR-9.3 export produces one audit entry for the whole operation, referencing its scope. *(Subject field, self-read scope, and granularity confirmed 2026-08-03.)*
- **FR-9.8** The system MUST NOT transmit user health data to any external service.
- **FR-9.9** The system MUST allow a user to withdraw their previously given consent to health-data collection, and MUST NOT record new health data for that user while consent is withdrawn — no new log entries, plan copies, selections, or estimation requests (FR-9.12). Existing records remain subject to FR-9.3–FR-9.5: editing and deleting existing entries (FR-8.7) and editing or deleting the subscriber's own existing customized plan copies stay available while consent is withdrawn, as exercise of the correction and deletion rights over already-collected data. This carve-out is the sole exception to FR-9.12's consent gate, covers only the owning subscriber, and never permits creating new records; consultant edits under FR-11.6 are refused while the engaged subscriber's consent is withdrawn, because a consultant edit is not the subscriber exercising a right. *(Threat-model-derived: SECURITY.md TM-P-2; correction-under-withdrawal clarified 2026-08-03; plan-copy scope and the consultant exclusion fixed 2026-08-03.)*
- **FR-9.10** On account deletion, the system MUST retain audit entries with the deleted account's identifiers replaced by an irreversible tombstone identifier — a keyed one-way derivation of the account identifier (SECURITY.md SEC-DATA-4) that also pseudonymizes archived audit batches (SEC-LOG-7) and keys the deletion ledger; audit entries never contain health values (SECURITY.md SEC-LOG-3), so nothing health-bearing survives. *(Resolves the audit-survival half of SECURITY.md SQ-5; derivation fixed 2026-08-03.)*
- **FR-9.11** The system MUST accept an account-deletion request submitted out of band from the account's verified email address when the requester cannot authenticate. Before executing, the system MUST verify control of that address by a single-use, time-limited confirmation token under SECURITY.md SEC-AUTHN-11 discipline, delivered to the address and matched to a registered account; that address-control proof and account match are the entire identity check — accounts hold no further caller-verifiable detail, and demanding more would either disclose account data or be theater. The system MUST send notice of the pending deletion to the address and surface it in any live session, and MUST wait 14 days, during which any authenticated session can cancel the request; after the window, FR-9.4 deletion executes. This channel MUST NOT restore access, MUST NOT satisfy or bypass any authentication factor (FR-2.13), and MUST NOT disclose any account or health data — export (FR-9.3) and correction (FR-9.5) requests without full authentication are refused under GDPR Art. 12(6)'s identity-verification allowance, and every refusal is logged. *(Resolves OQ-17.)*
- **FR-9.12** For FR-2.11, FR-9.2, FR-9.7, and FR-9.9, health data comprises: workout, food, body-weight, and body-measurement log entries; customized plan copies; and active plan selections. Creating or changing any of these is a health-data write — so selecting a plan or creating a copy requires prior consent and a verified email address — and reading any of them is a health-data access. The only exception to the consent gate is FR-9.9's correction carve-out over already-collected records. An AI estimation request (FR-8.12) is collection and processing of health data and is gated identically, though nothing is stored until the subscriber confirms. Account, subscription, and engagement records are personal data but not health data. *(Added 2026-08-03: fixes the health-data boundary that the consent, verification, audit, and admin-prohibition gates depend on.)*

### Administration

- **FR-10.1** The system MUST restrict plan authoring, verification, publication, and unpublication to accounts with the `admin` role, and MUST deny those actions to subscribers.
- **FR-10.2** The system MUST record an audit entry for every admin plan lifecycle action — create, edit, verify, publish, unpublish — capturing the acting admin, the action, the affected plan, and the time. *(Threat-model-derived: SECURITY.md TM-R-1, TM-T-5.)*
- **FR-10.3** The system MUST NOT allow an `admin` to read a subscriber's health data (FR-9.12) through the application. Admin administration views expose only administrative account fields — email address, role, email-verification state, MFA-enabled state, consent state, subscription periods, and consultant engagements — and admins MAY list and search subscriber accounts by those fields to perform FR-3.5 and FR-11.5. Operational emergencies below the application use the break-glass process (SECURITY.md SEC-OPS-1). *(Added 2026-08-03: makes the threat model's admin-capability assumption normative; SECURITY.md SEC-AUTHZ-9.)*

### Fitness Consultants

- **FR-11.1** The system MUST support fitness consultant / helper engagements for subscribers as a paid option in addition to the base subscription: an engagement is created by admin action (FR-11.5), payment is out of band in v1, and the subscriber's current engagement state is visible to them (DESIGN.md, consultant access). *(Reworded 2026-08-03 for testability.)*
- **FR-11.2** The system MUST NOT grant a consultant access to a subscriber's plans or health data unless that subscriber has an active paid consultant engagement with them.
- **FR-11.3** The system MUST allow a subscriber to end a consultant engagement, after which the system MUST revoke that consultant's access to the subscriber's data.
- **FR-11.4** The system MUST record an audit entry for each consultant access to a subscriber's health data, per FR-9.7.
- **FR-11.5** The system MUST create a consultant engagement only through an `admin` action that names the consultant and the subscriber, MUST treat the engagement as active from creation until it is ended under FR-11.3 or revoked by an `admin`, and MUST record an audit entry for each creation and administrative revocation. Payment for the option occurs out of band in v1 (OQ-1, OQ-18). *(Resolves the purchase half of OQ-13.)*
- **FR-11.6** Within an active engagement, the system MUST allow the consultant to view the engaged subscriber's selected plans, customized plan copies, and progress logs, and to edit that subscriber's customized plan copies; the system MUST NOT allow a consultant to create, edit, or delete log entries, and ownership of every copy remains with the subscriber (FR-7.2). Every consultant view and edit produces an audit entry per FR-11.4. *(Resolves OQ-12; SECURITY.md TM-E-3.)*

# Open Questions

- **OQ-1** RESOLVED (2026-08-01). Subscriptions are admin-granted periods: an `admin` grants, extends, or revokes a period (FR-3.5), a subscription is active exactly while the current time falls within a granted period (FR-3.6), and every change is audited. Payment collection is out of band in v1 — the system stays self-contained with no payments integration (SECURITY.md SEC-EXT-1). Self-serve purchase via a payment processor is deferred to OQ-18; the paid consultant option is recorded the same way (FR-11.5). FR-3.1–FR-3.4 are now fully testable.
- **OQ-2** RESOLVED (2026-08-01). No trial period, promotional tier, or free tier exists. Access requires a paid subscription; an `admin` MAY grant a time-boxed courtesy period through the ordinary FR-3.5 mechanism, which needs no additional machinery, states, or per-person trial tracking.
- **OQ-3** RESOLVED (SECURITY.md SQ-1, 2026-08-01). HIPAA is not applicable: the system has no covered-entity or business-associate relationship — it is direct-to-consumer, bills no insurance, and integrates with no provider — so no BAA is required and FR-9.7's audit obligation stands on its own. In scope for US users: the FTC Health Breach Notification Rule, state consumer-health laws (e.g. Washington My Health My Data), and CCPA/CPRA. GDPR/UK GDPR govern EU/UK data subjects, with GDPR-grade rights granted to all users. The breach-notification workflow is specified under SECURITY.md SQ-11; counsel review before launch is required.
- **OQ-4** RESOLVED (2026-08-01). Measurement fields are waist, chest, hips, upper arm, thigh, and body-fat percentage (FR-8.2). Units are configurable per account — metric (cm, kg) or imperial (in, lb) — covering measurements, body weight, and workout load; every record stores its value with its unit, and switching preference converts display only (FR-8.10). Body-fat percentage is unitless and bounded 0–100.
- **OQ-5** RESOLVED (2026-08-01). Two nutrition sources, both inside the system boundary: a bundled dataset imported at build or deploy time — initially USDA FoodData Central, public domain — searched in-app with a quantity (FR-8.11), and AI-assisted estimation from a food description or photo, presented as an editable, labelled pre-fill the subscriber confirms before saving (FR-8.12). Inference never leaves the system's cloud boundary and photos are transient (FR-8.13), so FR-9.8 holds as written; manual numeric entry is the estimate-free case of the same flow. Concrete model-service selection sits with SECURITY.md SQ-7 (topology); AI security rules are SEC-AI-1–SEC-AI-3, and OWASP AISVS applicability is now recorded in the epic.
- **OQ-6** RESOLVED (2026-08-01). One active plan of each type: at most one active exercise plan selection and one active diet plan selection per subscriber (FR-5.3, FR-6.4). A selection names a published plan or the subscriber's own customized copy; selecting another replaces it, logged history is never altered, and FR-8.5's daily comparison reads the currently selected diet plan exactly as written. The FR-9.6 disclaimer gates the first plan use, including first selection.
- **OQ-7** RESOLVED (2026-08-01). History is retained and displayed at full entry granularity for the lifetime of the account — no lossy aggregation. Presentation is trend charts over selectable ranges (4 weeks, 3 months, 1 year, all time) for body weight, each measurement field, and per-exercise workout load, each paired with an accessible data table (FR-8.14; DESIGN.md OQ-4 RESOLVED). The raw entry list with edit and delete (FR-8.7) remains.
- **OQ-8** RESOLVED. Password policy follows NIST SP 800-63B — 8-character minimum with 15 or more encouraged, no composition rules, no forced rotation, known-breached passwords refused — and anti-automation is exponential backoff throttling rather than account lockout, so no third party can permanently lock an account (SECURITY.md SEC-AUTHN-6, threat TM-D-2). Recovery: password reset by single-use token to the verified address, never bypassing an enabled second factor and always terminating existing sessions (FR-2.12); single-use recovery codes issued at MFA enrolment, with no admin-assisted MFA reset (FR-2.13); permanent unrecoverability on total factor loss, disclosed up front (FR-2.14); and privileged passkey recovery only by fresh invitation, with a two-passkey and two-admin minimum (FR-2.15).
- **OQ-9** RESOLVED. Subscribers may enable TOTP (RFC 6238) or a passkey as an optional second factor. SMS and email codes are excluded — NIST SP 800-63B treats SMS as a restricted authenticator, and an email code reduces the second factor to the security of the email account.
- **OQ-10** RESOLVED (2026-08-01). Verification is a one-time gate before first publication (FR-4.8); subsequent edits do not re-trigger it. The FR-4.4 citation rule remains a standing invariant — an edit may never leave a published plan without at least one citation — and every lifecycle action stays audited (FR-10.2).
- **OQ-11** RESOLVED. The accessibility conformance target is WCAG 2.2 AA (DESIGN.md, Accessibility; ARCHITECTURE.md, Note on DESIGN.md, which records that DESIGN.md resolves this question).
- **OQ-12** RESOLVED (2026-08-01). Within an active engagement a consultant views the subscriber's selected plans, customized copies, and progress logs, and edits that subscriber's customized plan copies — nothing else (FR-11.6). No log-entry writes, no messaging (a message channel would be a new requirements change), no access outside the engagement. Threat TM-E-3 is bounded: consultant write access is plan copies only, audited.
- **OQ-13** RESOLVED (2026-08-01). Purchase half: the paid consultant option is recorded by admin action (FR-11.5) with payment out of band. Onboarding half: consultants are vetted contractors or staff of the operator — identity and fitness credentials are checked out of band before any invitation, and the invitation carries the vetting record (FR-2.16). Removal is the FR-2.17 deprovision action. Whether a given consultant is an employee or a third-party contractor is an operator business matter with no system behavior attached.
- **OQ-14** RESOLVED (2026-08-01). Offline use is confirmed out of scope: the application requires a connection, no health data is cached on device (SECURITY.md SEC-RENDER-4 stands unamended), and no sync model exists. Backdated entries (FR-8.8) cover logging after the fact.
- **OQ-15** RESOLVED *(threat-model-derived: SECURITY.md TM-S-3)*. An account may be created and may authenticate before verification, but every health-data write is refused until control of the address is proven, and the address cannot be used in recovery until then (FR-2.11, SEC-AUTHN-8). The token is single-use, short-lived, and invalidated on use or replacement; resend is rate-limited and neither request nor response reveals whether an address is registered. Concrete token lifetime and resend interval were fixed when SECURITY.md SQ-3 resolved (SEC-AUTHN-8: 24-hour lifetime; resend at most once per minute and five per hour).
- **OQ-16** RESOLVED (2026-08-01) — dual control consciously declined *(threat-model-derived: SECURITY.md TM-T-5)*. The verifying admin MAY be the plan's author (FR-4.8). The residual risk — a single compromised admin can author, verify, and publish harmful content alone — is accepted, with compensating accountability: every lifecycle action audited (FR-10.2, SEC-LOG-6), admin accounts passkey-only (FR-2.8), and a two-admin minimum (FR-2.15) making post-hoc review possible. Revisit if the admin population or content risk grows.
- **OQ-17** RESOLVED (2026-08-01). The FR-2.14 trade stands: total factor loss never restores access and never bypasses MFA. What changes is deletion: a locked-out user may request account deletion out of band from the verified address, with identity checks, notice to the address and any live session, and a 14-day cancellation window before FR-9.4 executes (FR-9.11) — so a mailbox thief cannot silently destroy an active user's data, and the deletion right survives lockout. Export and correction, which disclose or alter health data, are refused without full authentication under GDPR Art. 12(6)'s proportionate-identity-verification allowance; that position is recorded for confirmation at the SQ-1 pre-launch counsel review. No identity-proofing escalation is introduced (it would be an external integration contradicting the self-contained posture).
